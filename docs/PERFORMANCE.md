# beta.5 备份与正式恢复速度对比

压缩分包将首次备份的内容 PUT 从 662 次减少到 7 次，正式恢复的内容 GET 从 662 次减少到 8 次。在每个 HTTP 请求额外延迟 25ms 的实验中，首次备份从 15.065 秒降到 5.703 秒，恢复准备从 23.465 秒降到 3.337 秒，分别约为原速度的 2.64 倍、7.03 倍。

没有额外延迟的实验中，恢复准备中位数从 3.553 秒变为 3.748 秒，没有测出稳定加速。分包需要额外的整包校验和解包；不能承诺所有低延迟局域网条件都更快。这些是模拟环境数据，不是私人 NAS 或 5 GB 真实备份的测速。

| 25ms | 小文件及一个大文件块变化 | 2.704 | 1.885 | 677 → 24 |

无变化时，两版新增内容上传均为 0。每次仍提交完整快照元数据：本负载 beta.4 上传 167,495 字节，beta.5 上传 318,515 字节。格式 3 的完整分包索引占用更多元数据空间。

增量场景仅修改一个小配置文件，以及 40 MiB 文件第二个 8 MiB 块中的一个字节。beta.4 新增 2 个对象，beta.5 新增 2 个分包，其余内容复用。计入元数据后，总 PUT 字节为 8,556,123 → 8,707,809；减少请求不代表每次增量的总上传字节一定更少。

恢复准备下载字节为 45,609,030 → 43,187,641。负载主要是难压缩的随机二进制，压缩收益有限；大块独立成包避免了恢复增量时额外下载同包的过期大块。恢复请求减少约 98.8%。

## 实验与验收

- Android 15/API 35 arm64 一次性 root 模拟器；本机 Python WebDAV 经模拟器 host-loopback 别名访问，HTTP/1.1 连接复用、TCP_NODELAY。不经 ADB 转发大流量。
- 同一负载：640 个不同的 4 KiB 文本文件、16 个不同的 64 KiB 随机文件、一个 40 MiB 随机文件、模块属性、符号链接和 FIFO，共 661 条文件记录。
- 基线从仓库 `v0.1.0-beta.4` 标签原样构建，仅加入同一性能测试入口。新版执行 beta.5 正式实现。每个延迟条件各 3 次，两版交替运行；每次使用空 WebDAV 存储和空恢复暂存。表格为各组中位数。
- 每次都运行首次备份、没有本机索引的无变化备份、内容增量备份，然后从所选增量快照调用正式 `Restore.prepare`。没有额外预取。恢复准备计时包含下载、完整性检查和正式准备，不包括两次系统重启的等待。
- 12 轮均完成正式恢复流程，并逐项核对文件类型、整文件哈希、权限、UID/GID、链接及 FIFO，每轮 3,303 项断言通过。APK、应用 CE/DE 配置与 LSPosed 六表另由双重启恢复验收覆盖。
- 所有数据均为合成夹具。没有访问私人 NAS，没有覆盖实体手机现用模块。
